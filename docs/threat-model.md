# VirtualSSD Security Threat Model

- **Status**: Production Specification
- **Revision**: 1.0 (2026-10-23)
- **Target OS**: Windows 11 x64 / Windows 10 x64

---

## 1. System Assets & Trust Boundaries

### Assets
1. **Raw Storage Data**: User block-level data written to virtual disks.
2. **Provider Credentials**:
   - Google Drive OAuth 2.0 refresh tokens, access tokens, client IDs, and optional client secrets.
   - Telegram bot token and numeric storage chat id.
   - Local provider databases and resumable-upload session URIs.
3. **Local Cache & Journal**: Uncommitted and committed data blocks stored on the local SSD.
4. **Manifests & Disk Metadata**: Mappings of disk sectors to remote cloud object IDs, BLAKE3 checksums, and revision numbers.
5. **Application IPC**: Tauri webview-to-Rust command channel. No separate service or named-pipe listener is shipped.

### Trust Boundaries
1. **Tauri Webview** <--> **Desktop Rust Backend**
   - Crossing: Tauri IPC command handlers in `apps/desktop/src-tauri`.
   - Rule: The backend exposes no network listener; commands are accepted only from the bundled webview. There is no privileged service IPC channel to harden.
2. **Multi-User Isolation**:
   - Crossing: Distinct Windows user accounts on the same machine.
   - Rule: Data lives under `%LOCALAPPDATA%\VirtualSSD`, which Windows ACLs isolate per user. Provider credentials are DPAPI-protected for the current user.
   - Under no circumstances should User B be able to decrypt User A's provider credentials.
3. **Cloud Providers (Google Drive & Telegram)**:
   - Treated as untrusted remote storage.
   - Chunks are verified via BLAKE3 checksums against the manifest before being accepted as valid.
   - Disks can opt into client-side AES-256-GCM encryption at creation. For those
     disks the provider sees only ciphertext and a ciphertext checksum; the
     per-disk key never leaves the machine. Disks created without encryption rely
     on provider-side account security for confidentiality.

## 2. Threat Analysis (STRIDE)

| Threat | Risk | Mitigation |
| :--- | :--- | :--- |
| **Spoofing** | Rogue process impersonates the UI client | The desktop backend exposes no network listener; commands come from the bundled Tauri webview. No separate service or named-pipe endpoint is exposed. |
| **Tampering** | Cloud provider or MITM modifies chunk data | BLAKE3-256 integrity verification on download before the chunk is accepted; encrypted chunks are checked against a ciphertext checksum and then authenticated by AES-GCM. Mismatches are surfaced as errors. |
| **Repudiation** | Ambiguous upload outcome leaves stale/corrupt manifest | Chunk upload must return a real object id/version (Google) or file id (Telegram) before the manifest is updated; manifest writes use temp rename + `.prev`. |
| **Information Disclosure** | Plaintext tokens or session keys leaked in logs/diagnostics | Provider credentials use zeroizing wrappers and redacting `Debug`; tokens are stripped from provider error text. The Diagnostics page shows the real backend `tracing` stream, which contains no tokens, session keys, or recovery-key material — key export/import is logged as an event without the key value. |
| **Denial of Service** | Network loss during write operations exhausts memory/cache | Bounded persistent cache; writes rely on the local WAL; sync is explicit rather than an unbounded background queue. |
| **Elevation of Privilege** | Path traversal in disk file paths or remote chunk IDs | Disk ids are parsed as UUIDs; credential/session paths are derived from validated provider ids; provider file names are generated by the adapter. |

## 3. Cryptographic Design

- **Chunk Integrity**: BLAKE3-256.
- **OAuth PKCE**: SHA-256 code challenge for the Google Drive authorization flow.
- **Provider Credentials**: Windows DPAPI (`CryptProtectData` / `CryptUnprotectData`) in current-user scope.
- **Client-Side Payload Encryption**: Optional per disk, fixed at creation.
  AES-256-GCM with a random 256-bit key; format `version(1) || nonce(12) ||
  ciphertext+tag`. The key is stored as a DPAPI-protected
  `disk_dir/encryption.key`, and only the 64-character hexadecimal recovery form
  is shown to the user. Missing keys fail closed and are never regenerated.
- **Recovery Key Transport**: Out of band only. The key is never uploaded with the
  manifest or chunks.
- **Credential Manager**: Not used; DPAPI-encrypted files under `%LOCALAPPDATA%\VirtualSSD\providers` are the implemented store.
